## Chapter 041

### EX-C041-01 — Choose outcomes for a stock lookup

Use `Option<&Shelf>` for the search. `None` says the search completed
and found no shelf. A reservation can use `Result<(), ReservationError>`.
In that contract a missing required shelf is `Err(UnknownShelf)`.
A caller can select a different shelf or report the rejected order.

### EX-C041-02 — Check exact depletion

```rust,edition2021
{{#include ../examples/reliability/src/stock.rs}}
let mut stock = Stock::new(5);
assert_eq!(stock.reserve(5), Ok(()));
assert_eq!(stock.available(), 0);
assert_eq!(stock.reserve(1), Err(InsufficientStock { requested: 1, available: 0 }));
assert_eq!(stock.available(), 0);
assert_eq!(stock.reserve(0), Ok(()));
assert_eq!(stock.available(), 0);
```

An exact request consumes the remaining quantity. A positive request
at zero fails before assignment. Zero consumes nothing.

### EX-C041-03 — Reverse a valid reservation

```rust,edition2021
fn release(total: u8, available: u8, request: u8) -> Result<u8, u8> {
    let held = total - available;
    if request > held {
        return Err(held);
    }
    Ok(available + request)
}

assert_eq!(release(255, 250, 5), Ok(255));
assert_eq!(release(255, 250, 6), Err(5));
```

The precondition makes `total - available` representable. After the
guard, `available + request <= available + held = total <= 255`.
If this becomes a public API accepting separate numbers, validate its
precondition or move the operation into the type that maintains it.

### EX-C041-04 — Keep validation active in release builds

```rust,edition2021
fn remaining_after(remaining: u8, requested: u8) -> Result<u8, u8> {
    remaining.checked_sub(requested).ok_or(remaining)
}

assert_eq!(remaining_after(3, 3), Ok(0));
assert_eq!(remaining_after(3, 4), Err(3));
```

Equality and the next larger request verify opposite sides of the
boundary. `checked_sub` has the same semantics in release builds.

### EX-C041-05 — Establish the sequence invariant

The initial sum of successful requests is zero. Every successful
request subtracts its quantity from availability and adds the same
value to the sum. Failure changes neither quantity. Thus the claimed
expression holds by induction. Exhausting initial pairs verifies
all starting counts for one request each. The proof addresses how
the relation persists after earlier requests.
