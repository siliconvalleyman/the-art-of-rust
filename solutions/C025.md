## Chapter 025

### EX-C025-01 — Test a zero-capacity pool

```rust,edition2021
{{#include ../examples/ownership/permits.rs}}
let pool = permits::Pool::new(0);
assert!(pool.acquire().is_none());
assert!(pool.acquire().is_none());
assert_eq!(pool.available(), 0);
```

Construct the pool with zero, check that both
acquisitions give absence, and check that available
is still zero. The checked subtraction rejects the
underflow before storing a new counter. The constructor
for a lease runs only on the accepted path. Creating
a guard despite failure would later increment capacity
without any corresponding acquisition.

### EX-C025-02 — Transfer a guard unchanged

Define a transfer as a function that takes a lease
by value and returns it by value. With capacity one,
scoped acquisition makes the free counter zero.
The transfer changes only who holds the lease. The
returned lease remains live and the count remains
zero. Calling `drop` on that lease returns the permit
once. Assert the count before and after dropping to
distinguish early cleanup from cleanup at the selected
point.

### EX-C025-03 — Restore a permit on early failure

```rust,edition2021
{{#include ../examples/ownership/permits.rs}}
fn check(pool: &permits::Pool, input: u8) -> Result<(), &'static str> {
    let _lease = pool.acquire().ok_or("no capacity")?;
    if input == 0 {
        return Err("invalid input");
    }
    Ok(())
}

let pool = permits::Pool::new(1);
assert_eq!(check(&pool, 0), Err("invalid input"));
assert_eq!(pool.available(), 1);
let lease = pool.acquire().unwrap();
assert_eq!(check(&pool, 0), Err("no capacity"));
drop(lease);
assert_eq!(check(&pool, 1), Ok(()));
assert_eq!(pool.available(), 1);
```

Return a no-capacity error immediately if acquisition
fails. After acquiring, keep the guard in a named
binding and check whether the input is valid.
Returning the invalid-input error ends the guard's
scope and restores one permit. Call with invalid
input on a free pool and assert the input error and
full free count after the call. Then hold the only
permit before calling again and assert the capacity
error. Manually changing the count on the error path
as well as dropping the guard could return the permit
twice.

### EX-C025-04 — Predict forgotten cleanup

```rust,edition2021
{{#include ../examples/ownership/permits.rs}}
let pool = permits::Pool::new(1);
let lease = pool.acquire().unwrap();
std::mem::forget(lease);
assert_eq!(pool.available(), 0);
assert!(pool.acquire().is_none());
```

Acquire from a capacity-one pool, forget the lease,
and assert that the next acquisition returns absence.
The count is zero and there is one outstanding
permit that can no longer be returned through an
accessible lease. Forgetting consumes the guard
without running the return transition. No second
owner is created and the proof still counts the
leaked reservation.

### EX-C025-05 — Return a finalization error

Hold the owner during the write. On a write error,
return a distinct write failure and let the guard
attempt ordinary cleanup. On success, call the
explicit finalizer and propagate its result. A fake
sink can record writes, finalization requests, and
cleanup attempts. In the three cases check that
finalization is skipped on a write failure, that
a finalization failure is distinguishable, and that
a full success reaches both operations. Require
evidence of the requested cleanup behavior separately
from the returned result. Checking only the destructor
would not expose the finalizer's error to the caller.

### Interview answers for Chapter 025

**IQ-C025-01.** The guard represents a real release
obligation. If it were created during a failed
acquisition, its destructor could free something that
was never owned or increase the available count above
capacity.

**IQ-C025-02.** Safe code can forget an owned guard,
and the process can also terminate without ordinary
cleanup. An unsafe abstraction must tolerate skipped
destruction without allowing invalid memory access,
even if that means resources can remain unreclaimed.
